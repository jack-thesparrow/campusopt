# CampusOpt — Data Model

## 1. Overview

All data used in the prototype is either:
- **Simulated**, generated by `backend/app/data/simulate.py` with a fixed
  random seed for reproducibility, styled to be realistic for NIT Mizoram
  (department list, hostel block naming, mess capacity ranges), or
- **User-supplied**, uploaded through the UI/API in the same schema.

There is no requirement to obtain real institutional data for the prototype
— realistic simulation is explicitly permitted by the problem statement.
Keep simulated and any real data in separate subfolders (`data/simulated/`
vs `data/raw/`) and never commit real student PII if it's ever used later;
see `Contributing.md` §6 for the data-handling rule.

Every table below is defined once here; pydantic schemas in
`backend/app/models/*.py` and pandas dtypes in `backend/app/data/loaders.py`
must match this document. If they diverge, this document is out of date —
fix it in the same PR that changes the schema.

## 5. Simulation rules (`simulate.py`)

The generator must be **seeded** (`--seed` CLI arg, default `42`) so runs
are reproducible, and must expose a `--scale` parameter matching the Small
/ Medium / Large sizes in `Architecture.md` §6.

Key realism rules baked into the generator:
- `attended_count = registered_strength * base_rate`, where `base_rate` is
  drawn from a Beta distribution centered around 0.75, shifted down ~15
  percentage points on `is_exam_week=True` (attendance drops before exams is
  the intentionally-injected signal the forecasting model should learn) and
  down further on `weather_flag='extreme'`.
- `actual_headcount = registered_diners * base_turnout`, `base_turnout`
  centered around 0.65–0.85 depending on `meal_slot` (dinner turnout is
  simulated higher than breakfast — another learnable signal), with a
  day-of-week effect (turnout dips on weekends when more students eat out or
  travel).
- Hostel `students.csv` is generated so that, at default scale, capacity is
  *slightly* tight but feasible (e.g. 95% occupancy) — the deliberately
  infeasible stress-test instance is a **separate, explicit generator flag**
  (`--force-overbook`), never the default output, so ordinary development
  runs are feasible by design.
- Course `registered_strength` values follow a realistic right-skewed
  distribution (many small tutorial sections, a few large first-year
  lecture courses).

## 6. Data flow between layers

```
simulate.py  ──writes──▶  data/simulated/*.csv
                                │
                                ▼
                     backend/app/data/loaders.py
                        (pandas DataFrames, typed)
                          │                    │
                          ▼                    ▼
                 prediction/*.py         optimization/*.py
              (train/test split,      (reads loader output +
               produces                ForecastResult as
               ForecastResult)         parameters, builds &
                                        solves model)
```

`loaders.py` is the single place that knows about file paths and CSV
parsing. Nothing in `optimization/` or `prediction/` should call
`pd.read_csv` directly — this is what makes both layers unit-testable with
in-memory fixtures instead of files (see `Contributing.md` §5 on tests).

## 7. Train/test split convention

Because both forecasting targets (`attended_count`,
`actual_headcount`) are time series, splits must be **temporal**, never a
random shuffle:

- Sort by `date`.
- Last 20% of dates (or last `N` days, whichever is specified per script) is
  the test set.
- No feature may leak future information — e.g. do not use a rolling average
  that includes the current or future row; shift by at least one day.

This is enforced in `prediction/train.py` via a shared
`temporal_train_test_split(df, date_col, test_frac)` helper — do not
reimplement splitting logic per model file.

See `Architecture.md` §7–8 for `ForecastResult` and `SolverResult`, which
